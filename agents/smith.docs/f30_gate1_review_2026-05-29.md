# Smith Gate 1 Review — F-30 Multi-Monitor Support
*Smith — 2026-05-29*

## Verdict: APPROVED with notes (1 must-fix-before-Morpheus, 4 non-blocking)

The stories are well-structured and Drew's OQ resolutions remove most ambiguity. The
underlying model — "single strip, single user-chosen display, hot-plug-safe" — is the right
HCI choice (one mental model, no surprise multi-strip behavior).

## Notes

### Note 1 — AC-F30-3-2: Fallback indicator must be visible on the strip, not buried in Settings (MUST-FIX before Morpheus arch)

**HEURISTIC:** #1 Visibility of System Status
**SURFACE:** Disconnect/reconnect fallback indicator
**ISSUE:** Current AC says: *"A persistent 'fallback active — display 2 unavailable' indicator
appears in **Settings** (or a tray/menu cue)."*

Settings is hidden behind a click. The user's chosen display has been overridden by the app,
silently, and the only way they'd notice is by opening Settings — which they won't do unless
something already prompted them to. This breaks the entire feature's user contract: "the strip
lives on the display I picked." When the app *can't* honor that pick, the user must know
**at-a-glance**, without opening anything.

**FIX:** Add an at-a-glance visual cue **on the strip itself** whenever the chosen display is
unavailable. Suggested options (Morpheus to pick a concrete design):
- A small warning glyph (e.g., monitor-with-slash icon) adjacent to the settings gear, with
  tooltip "Display 2 unavailable — showing on primary"
- OR a 2px colored top-border / accent stripe along the strip's edge while in fallback mode
- OR the settings gear itself adopts a colored dot/badge

The Settings indicator can *also* exist (for detail/explanation), but it cannot be the only
indicator.

**Rationale:** Users with the F-30 feature *enabled* have explicitly opted into multi-monitor
behavior. They've established the expectation "this strip goes on display X." Silently
violating that expectation is exactly the surprise-behavior pattern Smith blocks.

---

### Note 2 — AC-F30-1-2: OS-name fallback chain needs an explicit "garbage name" rule (Non-blocking)

**HEURISTIC:** #2 Match Between System and Real World, #6 Recognition Rather Than Recall
**SURFACE:** Display picker labels
**ISSUE:** AC says "prefer OS-reported display name; fall back to Display 1/2/3." In
practice, OS-reported names are frequently:
- Empty strings
- Generic placeholders ("Generic PnP Monitor" on Windows; "Unknown Display" on some Linux
  drivers)
- Identical for two physically distinct displays (two of the same monitor model)

If we display "Generic PnP Monitor" and "Generic PnP Monitor" as two picker options, the user
cannot tell them apart — defeating the purpose of preferring OS names.

**FIX:** Specify the fallback chain explicitly in AC-F30-1-2:
1. If OS name is non-empty, non-generic (not "Generic PnP Monitor" / "Unknown Display" /
   "Default Monitor"), and unique across the current display set → use OS name (e.g.,
   "Dell U2723QE")
2. If OS name is empty, generic, or collides with another display's OS name → fall back to
   "Display N — {resolution}" (e.g., "Display 2 — 1920×1080") so the user has *something*
   distinguishing
3. Primary display always carries the " — primary" suffix regardless of which label is shown

Morpheus may need to confirm what `screen_retriever` actually returns per-platform; if name
quality is too variable, just defaulting to "Display N — {resolution}" everywhere is also
fine and simpler. Don't promise quality the platform can't deliver.

### Note 3 — AC-F30-1: Disconnected-display behavior in the picker is unspecified (Non-blocking)

**HEURISTIC:** #5 Error Prevention, #6 Recognition Rather Than Recall
**SURFACE:** Settings display picker
**ISSUE:** AC lists "all currently-connected displays" but is silent on:
- What if the user's *previously chosen* display is currently disconnected — does it still
  appear in the picker (grayed out)? Or vanish?
- Can a user pick a disconnected display "in advance" so the strip moves there once it
  reconnects?

The "right" choice is a UX call, but the silence will lead to inconsistent implementation.

**FIX (recommended):**
- Picker shows **only currently-connected displays** (the simple model)
- The current persisted-but-unavailable choice is shown as a separate row at the bottom
  ("Currently set: Display 2 — unavailable") so the user understands why their chosen
  display isn't in the active list
- No "pre-pick a disconnected display" affordance; user can only choose from connected

This matches Heuristic #5 — you can't pick something that doesn't exist as an active option,
which prevents the "I picked it but nothing happened" error.

---

### Note 4 — AC-F30-3-3: Auto-return needs a brief visibility cue (Non-blocking)

**HEURISTIC:** #1 Visibility of System Status
**SURFACE:** Auto-return on reconnect
**ISSUE:** Drew chose immediate auto-return (OQ-1) — good, "it just works." But the strip
**jumping displays** mid-session, with zero indication of why, can confuse the user ("did
I just press something?" / "is my computer glitching?"). The jump itself is the only signal.

**FIX:** When the auto-return fires, the strip should show a brief, transient cue:
- The fallback warning indicator (from Note 1) fades out as auto-return completes
- OR a 2-second toast/tooltip near the settings gear: "Returned to Display 2"
- OR a brief animated highlight on the strip border as it appears on the returned display

This is a small polish item; Morpheus to incorporate during design. Non-blocking because the
behavior is correct; just the visibility-of-status layer is missing.

---

### Note 5 — AC-F30-2-2: "Remains sharp" is not testable as written (Non-blocking)

**HEURISTIC:** #10 Help and Documentation (testability)
**SURFACE:** Per-monitor DPI acceptance
**ISSUE:** "Text, icons, countdown remain sharp on the chosen display" is subjective. Trin
can't reproduce a "sharpness failure" reliably from this AC.

**FIX:** Rephrase as something Trin can pass/fail:
- "Strip renders at the chosen display's OS-reported DPI scale factor (e.g., 1.0, 1.25, 1.5,
  2.0). Verified by inspecting Flutter's `MediaQueryData.devicePixelRatio` matching the
  chosen display, not the primary's."
- Optionally: visual diff at 100%, 125%, 150%, 200% scale during UAT.

This is a wording fix only — the *intent* is right.
