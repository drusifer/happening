## Notes

### Note A — Indicator legibility floor at minimum strip height (Non-blocking)

**HEURISTIC:** #8 Aesthetic and Minimalist Design, #5 Error Prevention
**SURFACE:** `DisplayFallbackIndicator` (14×14 px at strip height ~28–36px)
**ISSUE:** At the minimum collapsed strip height (Neo to confirm exact px from
`getCollapsedHeight()`), a 14×14 icon may render at borderline legibility, especially at
100% DPI. The whole point of the on-strip indicator is at-a-glance recognition — if it's
squinty, Heuristic #1 (Visibility) is still partially defeated.

**FIX:** Define the indicator size as `min(14, stripHeight - 8)px` — i.e., always 4px
breathing room top and bottom, but never larger than 14×14. At 24px strip → 16px icon (max
clamped to 14); at 18px strip → 10px icon. Trin should add a visual-diff test at the minimum
strip height to verify the icon is recognizable as a "monitor with slash" glyph.

Cross-reference: This is the same accessibility concern Smith flagged in F-29 Note 3
(moon icon distinguishability at strip height). Same principle, different feature.

---

### Note B — Wayland event coverage may violate AC-F30-3-1's 2s budget (Non-blocking, document)

**HEURISTIC:** #4 Consistency and Standards, #10 Help and Documentation
**SURFACE:** Hot-plug detection on Wayland
**ISSUE:** AC-F30-3-1 says "strip falls back to current primary within 2s of the disconnect
event." If `screen_retriever` on Wayland does not emit disconnect events natively and we
fall back to a polling strategy (the architecture's noted mitigation), a 5s poll interval
violates the 2s AC.

**FIX (pick one before Neo starts):**
1. **Lower the Wayland poll interval to 1.5s** — meets the AC, costs a small amount of idle
   CPU. Acceptable.
2. **Document Wayland as exempt from the 2s budget**, mirroring F-28's graceful no-op
   posture. Update AC-F30-3-1 to say "≤2s on X11/Windows/macOS; ≤7s on Wayland (poll-based
   fallback)."

Recommendation: option 2. F-28 already established the precedent that Wayland gets
documented quality-of-service degradation rather than equal-feature parity. Drew has
accepted this trade-off before; same trade-off applies cleanly here.

Cypher to update AC-F30-3-1 wording before Phase A starts; not a re-gate.

---

### Note C — Deep-link tap target should be specific (Non-blocking)

**HEURISTIC:** #3 User Control and Freedom, #6 Recognition Rather Than Recall
**SURFACE:** `DisplayFallbackIndicator` tap behavior
**ISSUE:** Arch says "Tap → opens Settings → Display section (deep link)." Specify whether
this means:
- (a) Settings panel opens with the Display section auto-scrolled into view, OR
- (b) Settings panel opens at its top with Display section visually highlighted (e.g., brief
  flash/outline), OR
- (c) Settings panel opens at its top, Display section unchanged

Option (a) is the most actionable: the user lands directly on the control that fixes the
problem they just clicked on.

**FIX:** Specify option (a) in arch doc and as an AC-level requirement. Trin needs this to
write the widget test. Add: "Indicator tap → opens SettingsPanel, scrolls Display section
into the visible viewport, no further user action required to see the picker."
