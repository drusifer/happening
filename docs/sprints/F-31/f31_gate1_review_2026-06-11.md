## Notes

### Note A — Countdown click affordance (non-blocking, implementation note for Neo)
**Heuristic:** H6 Recognition Rather Than Recall  
AC-F31-3-2 makes the countdown text clickable to restore, but there is no visual affordance — the
countdown doesn't look like a button. This is acceptable because the → button is always present as
the primary restore path. However, Neo must use a **pointer cursor** on hover over the entire mini
widget (both countdown and → button areas) so users who hover discover the clickability without
needing to guess. No AC change needed; flag for Neo during implementation.

### Note B — Minimum touch/click target for hide button ⚠️ MUST-ADD AC
**Heuristic:** H5 Error Prevention  
AC-F31-1-5 says the hide button is "visually distinct" but sets no size floor. At strip height
(~28–36px), a narrow arrow button can fall below the 24×24px minimum click target that makes
desktop buttons reliable. Per the F-29 precedent (settings gear tap target), this must be explicit.

**Add to AC-F31-1-5:**  
> The hide button click/tap target is at least 24×24 px regardless of the button's visual size.

### Note C — Hide + Send-to-Back interaction (non-blocking, flag for Morpheus)
**Heuristic:** H4 Consistency  
The stories correctly mandate AC-F31-2-5 (mini widget always-on-top), but don't address what
happens if the strip is currently in send-to-back (always-below) mode and is then hidden:

- Scenario A: strip is in send-to-back (below windows) → user presses hide → mini widget should
  still be always-on-top per AC-F31-2-5. This means hide overrides the send-to-back z-order for
  the mini widget only, and show restores the pre-hide z-order.
- Scenario B: mini widget is visible → user activates send-to-back (if that's possible while
  hidden) — behavior undefined.

No story change needed. Morpheus must address the z-order override logic in arch.
