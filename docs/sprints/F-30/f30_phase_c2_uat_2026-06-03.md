## Non-Blocking Observations

### Observation 1 — `moveToDisplay` default impl uses `setPosition`, not `setBounds`
Arch doc §"Resize Strategy delta" specifies `setBounds(workAreaOrigin, workAreaSize.width × collapsedHeight)`. C1's default impl uses only `setPosition(workAreaOrigin)`, and the subsequent `_doCollapse()` issues the size change. Functionally equivalent: end-state is (workAreaOrigin, screenWidth × collapsedHeight). **Acceptable** — keeps `moveToDisplay` orthogonal to expand/collapse state and avoids issuing both setPosition+setSize when only one differs. Re-examine if a real-monitor switch shows flicker between move and resize.

### Observation 2 — Windows AppBar reseat is structurally correct but C3-blocked
`_onDisplayChangedInner` calls `moveToDisplay` *then* `onDisplayChangedExtra`, which on Windows runs `_reserveCollapsedSpace()` + repositions. The AppBar's internal rectangle is rewritten with new screen-width-aligned `rcLeft/rcRight` each time `_reserveCollapsedSpace` runs, so the reservation **should** rebind to the new monitor. **However**, the arch doc fallback (ABM_REMOVE+ABM_NEW cycle) is reserved for if this proves insufficient — that determination requires F30-C3 manual hardware testing on a real Windows secondary monitor. Flagged as expected.

### Observation 3 — DisplayService not yet passed to SettingsPanel
`main.dart` constructs `displayService` as a local; it is passed to `WindowService` but not yet plumbed through `HappeningApp` → `SettingsPanel`. **Acceptable** for C2 — F30-D1 (Settings UI) will add that plumbing. Recorded for D1 scope.

### Observation 4 — `setChoiceResolver` is the runtime-change hook for Settings UI
The wiring test "active display change calls strategy.moveToDisplay" drives the change via `displayService.setChoiceResolver(DisplayIdChoiceResolver(...))`. This is the exact contract F30-D1 must use when the user picks a different display in Settings: build a new `FingerprintChoiceResolver(choice)` and call `displayService.setChoiceResolver(...)`. Settings should also persist `chosenDisplay` via `SettingsService` in tandem. Recorded for D1 scope.

### Observation 5 — Hover-card golden is failing pre-existing
The 1 failing test (`hover card follows mouse X`) shows a 5.11% pixel diff. The failure PNGs in `app/test/goldens/failures/hover_card_alignment_*.png` were already modified in the working tree at session start (per session-start git status), so this is *not* C2-introduced. Recommend a separate visual-diff investigation outside this loop.
