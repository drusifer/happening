## Coverage Observations (Non-Blocking)

### Observation 1 — Fingerprint match uses exact double equality (Acceptable)

`PersistedDisplayChoice.matchIn` compares `widthLogical`, `heightLogical`, `xOffsetLogical`,
`yOffsetLogical` with `==`. In principle, floating-point equality can be brittle. In
practice, these values come from `screen_retriever` which returns OS-reported integer-aligned
logical pixel values per session — they're deterministic across a single Dart session.

Adding a tolerance (e.g., `(a - b).abs() < 1.0`) would silently downgrade some "strong"
matches to "exact" — which is fine — but could also misclassify a genuinely-different
display as the same one, weakening the fingerprint guarantee. **Acceptable as-is**; if a
real-world incident appears, revisit with a tolerance value calibrated to the observed
drift.

### Observation 2 — Weak-match callback wiring deferred to Phase C/F

`FingerprintChoiceResolver.onWeakMatch` is implemented and tested in isolation but not yet
wired into a production sink (logger or warning UI). Phase C2 (WindowService wiring) will
plug in the `Logger('DisplayService').warning(...)` call. **Acceptable** — interface is
ready; wiring is C2's responsibility.

### Observation 3 — `copyWith(clearChosenDisplay: true)` is a slight API smell (Acceptable)

The explicit clear flag is needed because `copyWith` already uses null to mean "no change."
This pattern is established in the codebase elsewhere; the test `copyWith clearChosenDisplay
clears the chosen display` documents the intent. **Acceptable** — explicit > implicit.

### Observation 4 — Probe (F30-A2-probe) still deferred to Phase C

Still on track for Phase C2 wiring when the real `screen_retriever` subscriber lands.
